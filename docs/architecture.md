# 系统架构

## 一、为什么是桌面端，不是 Android

早期规划为 Android + Kotlin + MySQL，已弃用。三个原因：

1. **数据敏感**。个人完整财务数据不该经过任何服务端。桌面端本地 SQLite 文件，数据不出机器。
2. **演示成本**。答辩/课程提交时，桌面应用直接打开即用；Android 需要装 APK、可能要开发者证书。
3. **首版只有一个用户**（作者本人）。做移动端等于为一个用户维护两套端。

若未来需要移动端，优先做"导出 + 只读查看"，而不是完整客户端。

## 二、技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 壳 | Electron | 学习成本低（前端 + Node），打包 exe 直接可用 |
| UI | 原生 ES Module + CSS | 零构建，改完刷新即生效，无工具链负担 |
| 图表 | ECharts | 开箱配色柔和，适合产品调性 |
| 数据库 | SQLite（better-sqlite3） | 单文件、零配置、支持 SQL 与事务 |
| AI | 智谱 GLM-4-Flash | 永久免费，兼容 OpenAI SDK，国内直连 |
| 报告导出 | HTML → 打印为 PDF | 不引重型 PDF 库，样式完全可控 |

**为什么不用 PySide6**：产品设计要求"奶油白、留白、柔和、适度插画"，
PySide6 是系统原生控件风格，做不到；PyQtGraph 的图表也是工程软件观感。
用 Web 技术做界面，视觉上限高一个量级。

## 三、分层架构

```
┌─────────────────────────────────────────────┐
│  展示层   Electron renderer（HTML/CSS/JS）   │
│           记账界面、成绩单、报告阅读          │
├─────────────────────────────────────────────┤
│  叙述层   LLM（GLM-4-Flash）                 │  ← 只写文字，不碰数字
├─────────────────────────────────────────────┤
│  事实层   facts.json（结构化指标快照）        │  ← 唯一的数据出口
├─────────────────────────────────────────────┤
│  计算层   core/（纯函数，无 IO，可单测）      │  ← 所有数字在这里产生
├─────────────────────────────────────────────┤
│  存储层   SQLite（复式记账）                  │
└─────────────────────────────────────────────┘
```

**铁律：数字只能从下往上流，AI 永远在最上层，且读不到原始流水。**

### 为什么 AI 只读 facts.json，不读原始数据

1. **防幻觉**：AI 手里没有原始数据，编不出细节
2. **省 token**：100 笔流水压缩成 20 个指标
3. **可复现**：同样的 facts，任何时间生成都应得到一致结论

## 四、进程划分

```
main（Node 主进程）
  ├─ SQLite 读写
  ├─ 文件导入导出（CSV）
  ├─ 备份/恢复
  └─ 调用 GLM API（API Key 不进渲染进程）

preload（contextBridge）
  └─ 暴露受限 IPC 接口，渲染进程不直接触达文件系统

renderer（浏览器环境）
  ├─ 界面
  ├─ ECharts 渲染
  └─ 只通过 IPC 取数据
```

API Key 必须存在主进程，用 `safeStorage` 加密后落盘，**不能写进渲染进程或前端代码**。

## 五、核心模块

### 5.1 复式记账核心（`core/ledger.js`）

纯函数，不碰数据库，输入分录数组，输出余额与报表。

```
记账（复式）
  ├─ 每笔交易至少两条分录
  ├─ 同一交易内 Σ分录金额 == 0（硬约束）
  ├─ 余额永不存储，永远实时计算
  └─ 期初余额 = 一笔 kind='opening' 的交易，不是一个字段
```

详见 [database.md](database.md)。

### 5.2 指标计算（`core/metrics.js`）

| 指标 | 公式 |
|---|---|
| 净资产 | Σ资产账户余额 − Σ负债账户余额 |
| 净现金流 | 期间流入 − 期间流出 |
| **生存月数** | 可动用流动资产 ÷ 近 3 个月支出中位数 |
| 负债率 | 总负债 ÷ 总资产 |
| 储蓄率 | 净现金流 ÷ 期间流入 |

**月均支出用中位数不用平均数**——一次大额支出会把平均数拉爆。

### 5.3 AI 叙述（`core/narrative.js`）

三个产物，频率不同：

| 产物 | 频率 | 输入 |
|---|---|---|
| 财务周报 | 每周 | 本周 facts |
| 月度财报 | 每月 | 本月 facts（渲染为可打印页面） |
| 成长与市场价值评估 | 每季度 | 能力档案 + 参考基准 |

### 5.4 名言系统（`core/quotes.js`）

**本地名言库，离线，有确切出处。AI 不参与生成。**

原因：LLM 会编造出处（"爱因斯坦说：记账是自由的开始"），
一旦出现假引用，产品的可信度归零。

```
quote {
  text, author, source,          // 出处必须具体到书名/篇章/演讲
  tags: [节制, 耐心, 开始, 复利],
  trigger: 可选的情境条件
}
```

选择逻辑：按当日/当周用户状态匹配 tag，**不随机**。
例：本周支出偏高 → 节制类；连续三周无创收 → 坚持类；首次创收 → 开始类。

## 六、时间与频率

| 频率 | 内容 | 触发方式 |
|---|---|---|
| 每日 | 一句名言 | 启动时 |
| 每周 | AI 财务分析 | 启动时检查，上周未生成则提示 |
| 每月 | 精美财报 | 启动时检查，上月未生成则提示 |
| 每季度 | 成长与市场价值评估 | 同上 |

**全部用惰性触发**（应用启动时检查周期），不用系统定时任务。
理由：不常驻后台、不产生无效 API 调用、用户主动查看时才消耗额度。

## 七、数据安全

- 数据库文件在用户目录，不上传
- 备份为单文件，可完整恢复
- 导出 CSV 供外部查看
- 发往 AI 的内容只有聚合指标，不含账户名、备注原文
- 不接入银行、不存支付密码、不自动交易
- AI 不能修改任何财务记录
